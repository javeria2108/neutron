# Software architecture

## Style
Modular monolith with **hexagonal / ports-and-adapters** boundaries. Functional core, imperative shell. Domain depends on nothing external; application orchestrates; adapters implement ports; UI presents state. Do not introduce microservices for a hackathon prototype.

## Recommended stack
Next.js App Router + TypeScript strict; React; React Flow (`@xyflow/react`); ELK.js for layout; Zod at boundaries; Vitest for unit/property tests; Playwright for E2E; Firebase AI Logic web SDK for hybrid inference; Firebase Hosting/App Hosting depending on deployment constraints. Recharts or lightweight charting for metrics. Firebase/Firestore optional until P0 is stable.

## Dependency rule
`domain` ← `application` ← `adapters` / `presentation`. Domain must never import React, Next, Firebase, browser storage, or AI SDKs.

## Route ownership and contracts

Follow NoorQuran's frontend ownership convention. Each Next.js route composes its screen. Place single-route components in its private `_components/` directory. When a second route uses a component, promote it to `src/features/<feature>/` and expose its public entry points through `index.ts`. Keep feature-specific pure transformations beside their callers. Component props stay with the component.

- `src/app/_components/` owns the workbench, inspector, graph rendering and replay views. Split by interaction or reason to change.
- `src/contracts/` owns types and wire schemas consumed across layers. Group these by capability. Keep SDK initialization and transport in `src/adapters/`.
- `src/application/` validates and applies edits and coordinates experiments. `src/domain/` owns deterministic model and simulation behavior, including run snapshots.
- NoorQuran uses workspace packages across several apps and a Nest API. Neutron currently has one Next.js app. These boundaries are directories within it. A future server can consume the same contracts; local inference and simulation need to run on the client.

## Data flow
UI event → application command → schema + semantic validation → immutable scenario snapshot → simulation engine → immutable RunResult → metrics selectors → UI. AI proposal → parse JSON → validate command → preview diff → user approval → application command. AI explanation → bounded evidence summary generated from actual RunResult → AI → response with checked evidence references.

## Core contracts (illustrative)
```ts
type ServiceId = string;
type EdgeId = string;
interface Scenario { schemaVersion: 1; id: string; nodes: ServiceNode[]; edges: DependencyEdge[]; workload: Workload; faults: Fault[]; seed: number; }
interface RunResult { engineVersion: string; scenarioHash: string; seed: number; events: SimEvent[]; metrics: RunMetrics; }
interface SimulationEngine { run(scenario: Scenario): RunResult; }
interface AICommandPort { proposeEdit(input: EditContext): Promise<ProposedEdit>; }
interface AIExplanationPort { explain(evidence: EvidenceBundle): Promise<Explanation>; }
```
Specify real interfaces in code after model review. Never silently change a persisted schema; version migrations.

## Implementation guidance
- Domain values immutable or copied at boundaries; no mutable singleton simulation state.
- Pure functions for event transitions; deterministic scheduler and seeded PRNG.
- UI keeps draft scenario separate from completed run snapshot.
- Simulation in Web Worker if main-thread responsiveness suffers; keep engine callable synchronously in tests.
- AI adapters return typed results with source and availability metadata; never import SDK in domain.
- Errors are typed, user-facing messages at presentation boundary; structured logs redact sensitive content.
- Use composition rather than inheritance; avoid generic abstractions until two concrete usages justify them.

## Key architectural decision
**Do not let AI invent simulation traces or numeric results.** Cloud model can summarize evidence generated by engine, and local model can propose validated edits. Every claim about run behavior should reference a metric or event.
